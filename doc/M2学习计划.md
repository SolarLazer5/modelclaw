## 一个总认知（先刻进脑子）

Agent 没有魔法。它就是**一个 while 循环 + 一份工具说明书**：

```
模型看到工具说明书（JSON Schema）→ 决定调用 → 返回 tool_calls（结构化 JSON）
→ 我们本地执行函数 → 把结果作为 role="tool" 的消息喂回去
→ 模型再看结果 → 继续调用 或 给出最终答案
```

LangChain 的 `AgentExecutor`、LangGraph 的 `create_react_agent`，内部都是这个循环。M2 手写它，M4 再用 LangGraph 重构——先手写后框架，你就永远知道框架在替你做什什么。

**自测题**
1. 工具调用的完整往返里，程序向 API 发了几次请求？（提示：看 app.log 的 `Sending agent request` 次数）

   `答：至少两次，第一次是调用模型，给模型用户问题，让模型思考选择调用的工具或者直接返回答案，第二次是喂给模型工具调用的结果让模型自己决定是否继续调用工具还是返回最终答案，所以如果涉及到工具的调用，最少需要调两次模型API`

   `【批改】✅ 基本正确。"至少两次"对，但可以更精确：请求次数 = 工具迭代轮数 + 1。注意一个细节：
   一次请求可以携带多个 tool_calls（阶段2知识点的多工具并发），所以统计单位是"轮"不是"个"。`

   `【标准答案】请求次数 = 迭代轮数 + 1。每轮循环发 1 次请求（该次请求可携带多个 tool_calls），
   若回复含 tool_calls 就执行工具、把结果挂回、continue 进入下一轮；直到某次回复不含 tool_calls
   （模型给出最终答案）循环才结束。所以：N 轮工具调用 → N+1 次 API 请求；0 次调用 → 1 次。
   验证书：app.log 里 "Sending agent request" 的条数。`

2. 工具的 JSON Schema 是给谁看的？（不是给程序，是给**模型**——它就是工具的「使用说明书」）

   `答：给模型看，模型根据Json Schema以及工具的doc注释来决定是否调用该工具，同时这个Json Schema还是模型调用工具时生成的Tools_calls结构的关键原材料参照`

   `【批改】⚠️ 基本正确但有一处事实错误：模型看不到 Python 函数的 doc 注释！docstring 只存在于
   你本地的源码里，模型的唯一信息来源是 schema 里的 description/parameters 字段。description
   就是 docstring 的"网络版"——必须写进 schema 模型才看得见。这一点在"description 写作艺术"
   精读项里反复强调过。后半句"tool_calls 的参照"表述模糊：schema 是模型生成 tool_calls 时
   遵循的格式约定（参数名、类型、required），不是运行时参照。`

   `【标准答案】给模型看。模型在 API 端只能读到本次请求里 tools 字段的那段 JSON——它对 Python
   函数长什么样、docstring 写了什么一无所知。schema 里的 description 是它判断"何时用、怎么
   用"的唯一依据（所以 description 是提示词工程，"百分数先转小数"这类经验必须写在这里）；
   parameters 是它生成 tool_calls 的 arguments 时遵循的格式约定。程序侧不消费 schema（执行
   靠 func），只负责把它塞进请求转发出去。`

## 阶段 1 · 工具层 `tools.py`（1 天）

**对照笔记**：`代理Agent.py` 的 `@tool` 装饰器 + docstring。我们手写的注册表是它的透明版。

精读顺序：

- [x] `TOOLS` 字典结构：`schema`（模型读的）+ `func`（我们执行的）。**职责分离**是核心设计
- [x] `calculator` 的 schema：对照 OpenAI 官方 function calling 文档的格式（`type: function` / `function.name` / `parameters` 是标准 JSON Schema）
- [x] description 写作艺术：为什么写「百分数请先转换为小数」？——**docstring/description 的质量直接决定模型会不会用错工具**，这是提示词工程的一部分
- [x] `_calculator` 的安全设计：`eval(expr, {"__builtins__": {}}, safe_names)`——内置函数全禁，只放行白名单 + math 模块
- [x] `_read_local_file` 的沙箱：`resolve()` 后检查路径前缀。**先 resolve 再判断**是关键（否则 `../` 穿越防不住）
- [x] `run_tool()`：为什么**永不抛异常**？（错误要以文本形式喂回模型，让它自己修正——这就是笔记里「模型会根据报错自行调试代码」的容错能力）
- [x] `_web_search` 的优雅降级：未安装/超时/无结果都返回文本而非崩溃

**动手实验**

```python
# 不写 CLI，直接驱动工具层（.venv/Scripts/python.exe 交互式）
from tools import run_tool, TOOLS, get_tool_schemas
run_tool("calculator", '{"expression": "sqrt(16) + 2**10"}')
run_tool("read_local_file", '{"path": "../.env"}')   # 观察沙箱拒绝
get_tool_schemas(["calculator"])                     # 看喂给模型的说明书长什么样
```

- [x] **加一个新工具**：仿照现有结构写 `get_weather`（可以返回假数据），注册进 TOOLS，在 config 的 `enabled_tools` 里启用，让 agent 用上它。这是本阶段最重要的练习——**体会「加一个工具只需动 tools.py + config」的扩展性**。

**自测题**

1. 为什么 schema 里 `parameters` 用 JSON Schema 而不是 Python 类型注解？（提示：这份 JSON 最终去了哪里）

   `答：因为这个Json Schema最终要作为网络请求发送给服务商，必须是Json类型而不是Python的类型注解`

   `【批改】✅ 正确，核心点命中（跨进程边界 + 可序列化）。可再补半句：消费者是模型而非程序，
   以及 Python 签名表达不了 description/required。`

   `【标准答案】因为它的读者是模型，不是 Python。schema 要序列化进 HTTP 请求体（tools 字段），
   跨越进程交给大模型阅读；JSON Schema 是 OpenAI 工具接口规定的"说明书格式"，已成各厂商兼容的
   事实标准。Python 类型注解是静态元数据：运行时无法 JSON 序列化、没有地方承载自然语言说明、
   表达不了 required 列表。TOOLS 字典里 schema/func 并列正是"对外协议"与"对内实现"的分离。`

2. 如果工具的 description 写得很模糊（比如就写「搜索」两个字），会发生什么？

   `答：模型会不知道是什么该调用它，或者说模型不知道调用它时该传什么样的一个参数`

   `【批改】✅ 正确。可以再补出"后果链"，把答案从"是什么"推进到"会怎样"：误调用 / 参数格式错 /
   多烧轮次。`

   `【标准答案】description 模糊的直接后果有三：① 该用不用——模型不知道何时该调它，干脆自己
   硬答（算错数）；② 不该用乱用——和别的工具混淆（该 calculator 的用了 web_search）；③ 参数
   格式错——"25%"不转 0.25 直接传，执行报 TypeError，错误文本回灌后模型再重试，白白多烧一轮
   迭代和 API 费用。所以 description 的质量直接决定工具调用成功率——它就是写给模型的提示词，
   这正是"description 写作艺术"被列为精读项的原因。`

3. 为什么 `python_repl` 被刻意排除在工具集之外？（笔记里有答案；想想生产环境的风险）

   `答：模型可以通过调用python_repl让模型自己写代码做一切事情，在生产环境中这是非常危险的`

   `【批改】✅ 正确。一句话把本质说清了。可再补具体化的攻击路径和正确姿势。`

   `【标准答案】因为 python_repl = 任意代码执行，前面所有安全边界在它面前瞬间失效：eval 白名单？
   repl 里 import os 根本不经过 eval；路径沙箱？os.remove 无视任何前缀检查。再叠加"LLM 输出不可
   信 + 提示注入"——攻击者不需要自己碰键盘，只要在对话里诱导模型调用 repl 写一段恶意代码即可。
   所以正确做法不是加限制而是用隔离承载：容器/gVisor/独立沙箱服务（无状态、无宿主机凭证、网络
   受控、超时强制），笔记里"切勿暴露到生产环境"的警告说的正是这个。`

## 阶段 2 · Agent 循环 `agent.py`（1.5 天）★核心

**对照笔记**：`代理Agent.py` 的 AgentExecutor 循环注释（1.4 节的新旧过程对应关系表）。

精读 `run_agent()`，逐行对照：

- [x] **消息流**（全文背诵级）：
  
  ```
  working = build_context(...)          # M1 资产：system + 摘要 + 裁剪后的历史
  循环:
      msg = ask_with_tools(working)     # 非流式，带 tools=schemas
      if msg.tool_calls:                # 模型要行动
          working += assistant 消息（带 tool_calls 字段）
          working += tool 消息（role="tool", tool_call_id=..., content=结果）
          continue
      else:                             # 模型有最终答案
          打印 reasoning + answer → 落库 → 返回
  ```
- [x] `tool_call_id` 的作用：tool 消息通过它挂回对应的 tool_call——**一次响应可以请求多个工具**（实测里出现过 2 tool calls），id 是对号的锚
- [x] `tc.model_dump()`：把 SDK 的 pydantic 对象转成可再发送的 dict——理解「消息历史里存的是协议格式，不是对象」
- [x] 落库策略：为什么只存 user + 最终 answer，工具消息只留在内存？（表 schema 不变 + 工具轨迹是过程不是结论；去 app.log 里找轨迹）
- [x] `max_iterations` 兜底：死循环防线。如果去掉它，什么情况会烧光你的 API 额度？
- [x] 与 `agent_scratchpad` 的对应：笔记里 AgentExecutor 用 `MessagesPlaceholder("agent_scratchpad")` 传递工具调用历史——**我们的 working 列表就是 scratchpad 的手写版**，逐条 append 的就是「之前的工具调用记录」

**动手实验**

- [ ] 打开 `config.json` → `logging.level` 改 `DEBUG`（或看 app.log），完整跟踪一次多工具任务的请求序列：每次请求里 messages 长了多少？
- [x] 破坏实验 1：`max_iterations: 1` 再跑计算任务，观察兜底报错
- [x] 破坏实验 2：把 `run_tool` 改成直接 raise，观察循环如何死掉——理解「永不抛异常」设计救了这个循环
- [x] 会话互通实验：`agent --session t1` 做任务 → `chat --resume t1` 问「刚才的结果」——**两个命令共享同一套会话系统**，为什么能互通？（工具消息没落库，chat 看到的是 user+answer，和普通对话无异）

**自测题**
1. Agent 循环和普通 chat 的 messages 结构差异在哪？（多了哪两种消息形态）

   `答：多了发送给模型的包含工具的Json Schema的消息，以及模型返回决定调用的工具的tools_calls消息`

   `【批改】⚠️ 有偏差，需要纠偏：JSON Schema 不是消息！它不进 messages 列表，而是作为请求的
   tools 参数每次随请求发送。messages 里真正新增的两种形态是"带 tool_calls 字段的 assistant
   消息"和"role=tool 的工具结果消息"。你把 schema 当消息、又漏掉了 tool 结果消息——这正是本
   阶段"消息流（全文背诵级）"要求背诵的内容，建议对照 run_agent 的消息流图重背一遍。`

   `【标准答案】messages 列表里新增两种消息形态：① 带 tool_calls 字段的 assistant 消息——模型
   的"下单"，content 可为空，tool_calls 记录它请求调用哪些工具、传什么参数；② role="tool" 的
   工具结果消息——我们的"回执"，content 是执行结果，tool_call_id 把它挂回对应的调用。注意：
   工具的 JSON Schema 本身不是消息，它作为请求的 tools 参数随每次请求发送，不进入消息历史。
   对照普通 chat：只有 user/assistant/system 三种角色消息，没有这两种结构。`

2. 如果模型第一轮就返回最终答案（0 次工具调用），循环走几遍？

   `答:刚进入循环，发现返回的消息中没有tool_calls，代表模型决定不调用模型而是直接输出答案，所以循环一遍也没走，直接一遍执行到底部输出最终答案（跳过if msg.tool_calls:块）`

   `【批改】✅ 结论正确（走 1 遍），但表述有口误："循环一遍也没走"和"直接一遍执行"自相矛盾——
   循环体确实执行了一次：ask → 判 tool_calls 为空 → if 块跳过 → 走底部打印/落库/return。
   面试时这种表述要捋顺。`

   `【标准答案】走 1 遍。流程：进入循环 → 发第 1 次请求 → 回复不含 tool_calls → if msg.tool_calls
   不成立 → 执行循环体底部的"最终答案"分支（打印 reasoning + answer、落库、return），循环结束。
   注意措辞：是"循环体执行了一次"，不是"循环没走"——else/底部逻辑就在循环体内部。`

3. 思维链（reasoning_content）在非流式响应里是怎么拿到的？（`getattr(msg, "reasoning_content", "")`——为什么不流式了？）

   `答：ask_with_tools是非流式模型调用，调用后，通过调用getattr直接取出msg对象中reasoning_content属性的值`

   `【批改】⚠️ 不完整。"怎么拿"答了（getattr 容错取值），但题目第二问"为什么不流式了"没有正面
   回答——这恰恰是本题的核心：Agent 循环必须等完整响应才能做结构化决策。`

   `【标准答案】非流式响应是一次性返回完整消息对象的，reasoning_content 作为消息的一个字段
   直接挂在上面；用 getattr(msg, "reasoning_content", "") 取值并给默认值，是因为该字段只有
   DeepSeek 风格带思维链的模型才返回，其他模型没有此属性，直接 .reasoning_content 会
   AttributeError。至于为什么 Agent 循环用非流式（而 chat 用流式 ask）：流式的内容是分片到达的，
   而循环必须对模型的回复做结构化判断——有没有 tool_calls、要不要继续迭代、arguments 是否完整
   ——分片状态下无法中途决策，只能等流结束拼完再判断，那还不如直接非流式一次拿全。代价是用户
   看不到逐字生成，所以用 _render_tool_call 的工具面板补过程感。`
