# 第 1 级：纯向量检索（翻车现场）——详细解释（复习用）

> 本文档基于一次完整的学习对话整理，记录"纯向量检索翻车"事件的完整因果链、
> 学习过程中被纠正的四个误解、以及后续级别为什么能救回正确块。

## 一、事故现场还原

**背景**：M3 开发第一版 `ask`，检索只有纯向量通道（没有 BM25、没有重排）。

**操作**：终端执行

```bash
modelclaw ask "config.json 里 retry 组有哪些字段？各自什么作用？"
```

**预期**：知识库中有 `doc/config字段说明.md`，其第二章完整写着 retry 组的 4 个字段（max_attempts 等），模型应照此作答。

**实际**：模型回答「知识库中没有相关内容」。

**排查**：打印该次检索的完整距离排行榜（实测数据）：

```
排名   距离      块
─────────────────────────────────────────────
第1名  0.261   config字段说明.md#0   ← 文档开头（标题+项目简介）
第2名  0.334   README.md#16          ← 配置流转图
第3名  0.345   README.md#25
第4名  0.347   README.md#8
 ...
第N名  0.457   config字段说明.md#3   ← 正确块（retry 章节）
```

正确块连前 12 名都没进。

## 二、逐词拆解

**「正确块」**：知识库共切成 107 个块，只有 `config字段说明.md` 的 3 号块真正包含 retry 组的字段说明。它是本问题的"正确答案载体"。

**「排在十名开外」**：向量检索的工作方式是——问题转向量 → 与全部 107 个块各算一次距离 → 排名 → **只取前 4 名（top_k=4）拼进提示词**。正确块排在十名开外 → 根本没进提示词 → 模型看到的 4 个块里确实没有答案 → 按系统提示词规则（"没有就直说，不要编造"）诚实拒答。

**「翻车」翻的是谁**：失败的不是模型，是**检索**。模型只拿到 4 个无关块，按规则只能拒答——它既诚实又正确。印证了笔记里的那句话："当问答返回错误结果时，通常不是语言模型出错，而是检索步骤出错。"

> **排查铁律**：RAG 的错误链条是 检索错 → 上下文错 → 答案错。
> 排查永远从「模型到底看到了哪几个块」开始，而不是怀疑模型。

## 三、根因拆解（为什么会排这么后）

对比两张牌：

| | 正确块（retry 章节） | 第 1 名（文档开头标题块） |
|---|---|---|
| 内容开头 | `## 二、retry —— 重试策略配置 ...` | `# config.json 字段说明` |
| 问题强信号词「config.json」 | **出现 0 次** | ✓ 命中 |
| 问题强信号词「字段」 | **出现 0 次** | ✓ 命中 |
| 问题弱信号词「retry」 | ✓ 出现（标题+正文） | ✗ 0 次 |

**机理**：问题的向量方向被「config.json」「字段」主导；标题块两个关键词全占 → 距离 0.261 排第 1；正确块字面全 miss → 0.457 十名开外。bge-small 是 24M 参数的小向量模型，语义区分能力弱，更多被字面特征带着走 → **关键词密度高的无关块反超了语义正确的答案块**。

**深层认知（embedding 模型的本质）**：

> embedding 模型通过训练学会"互为问答的文字向量拉近"，但它天然偏爱**字面重合**这种最强、最容易学的信号；「意思相同但用词不同」的深层语义是弱信号，小模型学不好。

## 四、关键纠错（学习过程中被纠正的四个误解）

**误解 1：嵌入模型参与检索时的距离计算** ❌

嵌入模型的出场时机只有两次：

```
入库时：文本块 → [嵌入模型翻译] → 向量 → 存库        （翻译官下班）
查询时：问题   → [嵌入模型翻译] → 向量               （翻译官再上一次班）
检索时：问题向量 vs 库中所有向量 → 算距离            （纯数学，模型不在场）
```

`MATCH` / `<=>` 做的只是"几百上千个浮点数的距离计算"——是 sqlite-vec/pgvector 在跑纯算术，没有任何神经网络参与。**这正是向量检索快的原因**：模型负责理解（编码），数据库负责查找（算距）。

**误解 2：BM25 是一个"模型"** ❌

BM25 是统计排序算法——没有训练、没有神经网络、没有权重文件，本质是一套基于词频的打分公式（tf-idf 家族）。注意区分：嵌入模型和重排模型是模型，BM25 不是。

**误解 3：BM25 靠数"config.json"和"字段"** ❌

正确块里 "config.json" 是 **0 次**。BM25 救回正确块靠公式的两板斧：

| 维度 | 统计范围 | 规律 | 本项目实例 |
|---|---|---|---|
| IDF（稀有度） | 横看全库：词在多少块出现过 | 出现的块越多 → 权重越低（满大街的词不值钱） | "config.json" 散落一堆块 → IDF 低；"retry" 只集中在极少数块 → IDF 高 |
| TF（词频） | 竖看单块：词在这块内出现几次 | 块内出现越多 → 该块得分越高 | "retry" 在正确块标题+正文多次出现 → 猛涨分 |

正确块被顶上去的机制 = 「retry」**全库稀有（IDF 高）× 正确块内密集（TF 高）**。
（BM25 还有第三板斧：长度归一化，防长文档占便宜，了解即可。）

**误解 4：两个通道是"串联"** ❌

不是"先算 distance，再用 BM25 加工距离结果"（那就成了向量检索的输出是 BM25 的输入）。
正确结构：

```
                  ┌─ 向量检索（语义通道）→ 排行榜 A ─┐
问题 ────────────┤                                ├─ RRF 融合 → 候选 12 块 → rerank → top k
                  └─ BM25 检索（关键词通道）→ 排行榜 B ─┘
```

两路**各自检索、各自排名，数据上互不消费对方的输出**，只在最后交换排名（RRF 融合）。
注意区分两个"联"：代码执行顺序是串行的（单线程三行依次跑），但**数据依赖**是并联的——
这个性质意味着生产系统可以把两路真正并行化（总耗时 = max(A,B) 而非 A+B）。
极限情况：BM25 用的是原始问题文本，连 `embed_query` 都不必等，第 0 毫秒就能开跑。

## 五、完整救援链路（第 1 级 → 第 2 级 → 第 3 级）

嵌入模型把问题译成向量时，「config.json」「字段」主导了向量方向（小模型语义弱）
  → 纯向量通道里正确块十名开外
  → BM25 通道里，「retry」高频稀有词把正确块顶进排行榜前列
  → RRF 融合，正确块靠 BM25 通道的排名挤进候选 12 块
  → reranker（本地 bge-reranker-base，cross-encoder）把问题和候选块拼在一起精读，
    确认它确实回答了问题，排进 top k
  → **阈值闸门**：top1 得分 < 0.1 → 直接拒答（零 LLM 成本）；≥ 0.1 → 拼上下文交给大模型

三级为什么有效——**盲点的互补**：

| 通道 | 擅长 | 盲区 |
|---|---|---|
| 向量检索 | 语义改写、同义表达 | 字面精确匹配（被本案击中） |
| BM25 | 字面、稀有词精确命中 | 换说法的改写 |

两者失败的模式正好错开，融合才有数学基础。召回阶段的使命不是"精确"，是"**别漏**"——
从 10 万块里几十毫秒圈出 50 个候选，决定 reranker 的天花板（垃圾进垃圾出）。

**历史视角**：关键词检索是 50 年的老技术（TF-IDF 1970s，BM25 1994），向量检索是 2020 年前后的颠覆者。真实叙事不是"向量检索要人扶"，而是"向量检索闯入后发现新老结合最强"——hybrid retrieval + rerank 正是 Elastic、Azure AI Search、Pinecone 官方都在推的标准架构。**"不像生产环境"的这套，恰好就是生产环境。**

## 六、与更高级思想的关系（不是替代，是上下游）

- **Small-to-Big（父子块）**：改的是"切分和返回什么"，检索管线（混合召回+重排）原样保留，回答"命中后给模型多大上下文"。
- **Agentic RAG**：把检索包成工具交给 Agent 自主调用——工具内部还是这套 `retrieve()`。
  M2 的 Agent 循环 + M3 的检索管线 = Agentic RAG 的两个零件。
- 生产上 80% 的场景停在朴素 RAG 或 +父块扩展，Agentic 因不可控性在客服/内部工具场景反而是减分项。

## 七、亲自动手清单（复现才有体感）

1. 打开 `rag.py`，把 `retrieve()` 临时改成纯向量（直接 `return store.search(vector, k)`，跳过 BM25 和 rerank）；
2. 跑 `modelclaw ask "config.json 里 retry 组有哪些字段？"`，亲眼看它翻车；
3. 写小脚本打印全库距离排名，找到正确块排第几；
4. 恢复代码；
5. （建议）分别打印两个通道各自的排行榜，对比同一个块在两边的名次差——
   "一个通道漏掉的被另一个通道捞回来"的体感，看十遍文档不如亲手打印一次。
