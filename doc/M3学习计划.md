## 一个总认知

RAG 的全部秘密就一句话：**「先检索，后回答」**——把问题翻译成向量，去库里面找最相关的几段文字，塞进提示词让模型照着答。它解决的是大模型两个绝症：**知识截止**（不知道新东西）和**幻觉**（不知道就编）。

```
ingest:  文档 → 切分(chunking) → 嵌入(embedding) → 向量库
ask:     问题 → 嵌入 → 检索(retrieve) → 重排(rerank) → 拼进提示词 → 流式回答 + 引用来源
```

## 阶段 1 · 嵌入层 `embeddings.py`（1 天）

**对照笔记**：`基于文档的问答.py` 的 `OpenAIEmbeddings` —— 我们把在线 API 换成了本地模型。

- [x] 理解 embedding 的本质：把一段文字压成 512 个浮点数，语义相近的文字向量距离近

  [^]: ：**embedding 是一台"语义坐标机"——任何文字进去，都得到一个固定维度的坐标；从此比较两段文字的意思，就变成了在空间里算两个点的距离。**

- [x] `HF_ENDPOINT` 为什么必须在 import 之前设置？（环境变量在 huggingface_hub 加载时读取）

  [^]: **huggingface_hub 只在被 import 的那一刻读一次 HF_ENDPOINT 环境变量，之后就把值"焊死"在内存里了**

- [x] 懒加载单例：为什么模型不放到模块级直接加载？（torch 启动要几秒，不相关的 CLI 命令不该付这个代价）

  [^]: **懒加载把"加载模型"从 import 的"过路费"变成按需的"服务收费"，单例缓存确保这份收费整个进程只收一次**

- [x] `normalize_embeddings=True`：归一化后点积=余弦相似度，这是为什么 `search` 里的距离可以直接当相似度用

  [^]: **归一化（把每个向量缩放到长度 1）→ 余弦相似度公式里的分母消失 → 点积直接等于余弦相似度 → 检索排序时算一次点积就完事**。

- [x] **reranker 是什么**：bi-encoder（嵌入模型）把问题和文档**分开**编码算距离；cross-encoder（reranker）把问题和文档**拼在一起**读，打分更准但更慢——所以只用于召回后的几十个候选

  [^]: **Bi-encoder 是"分开速读"**：各自编码成向量比距离，快但粗；**cross-encoder 是"合卷精读"**：问题和文档拼在一起逐对交给大模型打分，准但慢。所以工程上的答案是分工——用快的在百万文档里捞回几十个候选，再用准的对这几十个排序取前几个，速度与精度兼得。

  

**动手实验**

```python
from embeddings import embed_texts
vecs = embed_texts(["重试策略", "失败后再试一次", "红烧肉的做法"])
# 算两两余弦相似度，验证「重试策略」和「失败后再试」更接近
```

**自测题**

1. 512 维是怎么定的？换模型（如 bge-large-zh 是 1024 维）要动哪些地方？（提示：`EMBEDDING_DIM`、vec 虚表、已有数据怎么办——重建）

   `答：维度是模型的出厂属性（small=512、large=1024），数据库在建表时把它固化成 schema；所以传统硬编码写法下换模型要同步动 EMBEDDING_DIM 常量、重建 vec 表、并重新嵌入全部数据（新旧向量是两个坐标系，无法共存）。好的设计是把维度改为运行时从模型推导、让向量库从首批数据自学维度——把换模型的操作压缩成"改配置 + 重建数据"两件事，消灭常量同步这类人为失误。`

2. 本地 embedding 的三个好处？（成本、隐私、离线可用）一个代价？（首次下载 + 本机算力）

   `答：略`

3. 维度的作用？既然最终都是比余弦相似度，那为什么换维度后要重灌入，直接算相似度不行吗？

   `答:余弦相似度的公式本身要求两个向量一样长,即cosine(a, b) = (a₁b₁ + a₂b₂ + ... + aₙbₙ) / (|a| × |b|)，点积的操作是：两个向量第 1 个数配第 1 个数、第 2 个数配第 2 个数……第 n 个配第 n 个，逐项相乘再相加。一个 512 维向量和一个 1024 维向量，连"谁配谁"都确定不了，算式对不同维度的向量没有定义，同时如果换了另一个模型，碰巧也是 512 维，检查会放行，但旧向量照样作废！因为两个不同模型即使维度相同，坐标轴也完全不同，所以严格说，只要换了模型（不管维度变没变），知识库就该重建`

## 阶段 2 · 切分 chunking（0.5 天）

- [x] 读 `rag.py` 的 `_chunk_text`：`RecursiveCharacterTextSplitter` 的分隔符优先级 `["\n\n", "\n", "。", "，", " ", ""]`——为什么这个顺序？（尽量在语义边界切：段落 > 行 > 句子）

  [^]: 这个顺序就是一张**"语义完整度的阶梯"**：从段落（作者划分的最完整单元）逐级退到行、句子、分句，最后用空串保证任何文本都能被切开。切分器每遇到一个超大块，就从阶梯顶部重新往下试，直到切出大小合规的块。顺序的意义在于——**绝大多数块落在高优先级边界上，语义单元得以完整保留，而这是后面向量检索能命中的前提**。

- [x] `chunk_size=500` / `chunk_overlap=50` 的权衡：块太大（检索不精确、稀释）vs 太小（语义不完整、上下文断裂）；overlap 是为了跨块的句子不被切断

  [^]: `chunk_size=500` 是**每块最多装 500 字符**,`chunk_overlap50` 就是让**相邻两块共享 50 字**,`chunk_size`过大，**向量被稀释**(向量中的关键信息占比减少，准确率下降),`chunk_size`过小，**向量化失去** (检索到了也答不了,内容不完整),所以 **chunk_size等于500是个折中**,`chunk_overlap`保证了**自然的内容边界**，总结：`chunk_size=500` 是在**装得下完整语义**和**不被无关内容稀释**之间**取的平衡点**——**太大，关键信息在向量里被淹没**、检索不精确；太小，**句子不成形**、检索到了也答不了。`chunk_overlap=50` 则是**为切块的人为边界买的保险**：无论窗口切在哪，**被劈开的句子都能在相邻块中完整保留一份**，代价**约 10% 的额外存储**。

## 阶段 3 · 向量库 `rag_store.py`（0.5 天）

- [x] 两张表设计：`chunks`（文本）与 `vec_chunks`（向量虚表）为什么分开？（sqlite-vec 的虚表只存向量，靠 rowid 关联——向量数据库的「索引与数据分离」思想）

  [^]: `chunks` 与 `vec_chunks` 分开，是因为**在sqlite-vec中**， `vec0` 虚表**只懂向量**、**存不了也用不好文字**；而**向量检索和文字存取是两种完全不同的数据操作**，值得各自用最适合的结构。**两张表靠写入时约定的同一个 rowid 关联**，查询时**向量索引先筛出最近的几行、再联查回文字**。这就是向量数据库"索引与数据分离"思想的最小实现——代价是写删查都要走两遍，换来的是两边各自最优的性能，以及 **BM25 这类纯文本通道的零成本复用**。

- [x] 读懂 `search()` 的 SQL：`MATCH ? AND k = ?` 是 sqlite-vec 的 KNN 语法；JOIN 回 chunks 取文本

  [^]: vec0 虚表用 `MATCH + k` 的**私有语法**在自己的**向量索引里完成近邻筛选**并**产出** `distance`，再通过 `rowid = id` 的 INNER JOIN 进行双表拼接，从而同时得到对应文字和向量距离，这些操作融合在一行sql语句中完成。

- [x] 「派生数据」概念：向量库删了不心疼，`ingest` 一遍就重建——这决定了它该放本地还是放共享库

  [^]: 向量库是**"派生数据"**——由文档原文经固**定流水线计算而来，**删除后重**跑一次 `ingest` 即可无损重建，**所以 `clear` 敢连表 DROP、换模型敢报错不兼容。正因为"丢了不心疼"，它的存储位置只需要权衡v重建成本与访问模式：单用户工具默认零配置的本地文件，只有共**享访问或重建代价高昂时才**升级到共享数据库。整个 RAG 系统对向量"可随意处置、对原文小心翼翼"的不对称设计，都是从这个分类推导出来的。

### 第 2 级：混合检索（向量 + BM25）
- [x] 读 `rag.py` 的 `_bm25_search` + `_rrf_fuse`

- [x] BM25 是什么：基于词频的关键词匹配（tf-idf 家族），和向量互补——向量懂语义不懂字面，BM25 懂字面不懂语义

  [^]: BM25是一个用于“关键词检索”的算法，效果是，算IDF值和TF值，然后在整合两个值，最终做一个排名，IDF和TF的解释如下表格

  | 维度              | 统计范围                                 | 规律                                                | 本项目实例                                                   |
  | :---------------- | :--------------------------------------- | :-------------------------------------------------- | :----------------------------------------------------------- |
  | **IDF（稀有度）** | 横看全库：这个词在**多少个块**里出现过   | 出现的块越多 → 权重越**低**（满大街都是的词不值钱） | "config.json" 散落在 README 一堆块里 → 权重低；"retry" 只集中在极少数块 → 权重高 |
  | **TF（词频）**    | 竖看单块：这个词在**这一块内**出现了几次 | 块内出现越多 → 该块得分越**高**                     | "retry" 在正确块里出现多次（标题+正文）→ 正确块猛涨分        |

- [x] 中文分词坑：CJK 单字（有/哪/什/么）全是噪声，**只用二字组（bigram）**后 retry 块从第 8 升到第 4。读 `_tokenize` 的注释

  [^]: BM25 的排名质量完全取决于分词质量。单字分词把"有/哪/什/么"这类几乎每个中文块都出现的字直接暴露给 BM25：它们 IDF 趋零甚至为负（关键的“字段”被分为“字”“段”，所有快，包括正确块，IDF骤降）,`_tokenize` 改用相邻二字成组后,稀有度跃升，噪声项不再独立计分,因此二字组是"携带语义的最小统计单元"。

- [x] RRF 融合公式：`score = Σ 1/(60 + rank)`——为什么用排名融合而不是直接加分数？（两个通道的分数量纲不同，排名是无量纲的）

  [^]: 向量通道和BM25通道比较出来的排名的值，在数学上是不同的概念,即使将BM25的排名榜单值进行归一化后，BM25榜单中每个排名的差值，和向量通道的差距值，也不能放在同一个天平上，因此采用score = Σ 1/(60 + rank)这个公式对“排名”本身进行融合

- [x] 结果：有进步但仍不够稳（双通道都命中的块还是会挤掉单通道的正确块）

  [^]: 第 1 级进行**向量化检索通道，**证明"**语义信号会漏（**即**小向量模型对于块与问题的同字段过于敏感，**而**对于语义理解的完整度的欠缺导**致检索结果**排名的不准确）**"→ 第 2 级用**BM25关键词检索通道**结果与**向量化检索通道结果**融合**解决"漏"，**但暴露了"**累加制偏爱共识、单通道正确块会被双通道平庸块挤掉"**的新问题 → 这个问题在召回层无解（投票机制的天花板），必须由**第 3 级重排**把"候选池里的排序权"从通道手里收回来，**交给真正读了题的人(神经网络，即模型)。**

### 第 3 级：重排序 rerank（生产级答案）
- [x] 读 `embeddings.py` 的 `rerank()` 和 `rag.py` 的 retrieve-then-rerank 流水线

- [x] 为什么 rerank 是质变：cross-encoder 把「问题+候选块」拼起来一起读，对关键词型问题精度碾压双编码器

  [^]: "双编码器"就是向量检索的学名：问题与块**分开编码、向量比对**，检索时模型已离场。cross-encoder 换成**问题与块拼合编码、同场模型精读**的一次神经网络，第一次让"这段文字是否在回答这个问题"成为可计算的判断

- [x] 实测：rerank 后 retry 块得分 0.806 进入 top-4，模型完整答出 4 个字段

- [x] 为什么 rerank 放在召回之后而不是全库？（cross-encoder 慢，只能跑几十个候选）

- [x] **完整链路默写**：`向量召回 + BM25 召回 → RRF 融合取 top-12 → cross-encoder 重排取 top-4 → 阈值过滤 → 拼提示词`

## 本补丁的真实 bug 清单（复用 M1 的排障思路）

1. **类型注解在导入期求值**：`rag.py` 的类型标注 `store: RagStore` 在 import 时就要求名字存在——`py_compile` 编译不执行所以漏检。教训：**验证要用 import/运行，不只是编译**。
2. **空表 UndefinedTable**：pgvector 后端的表是「首次写入时按维度懒创建」的，空库状态下 `has_source`/`list_sources` 直接炸。防御：所有读路径容忍表不存在。对照 M1 的「先想空态」。
3. **Qwen3-Embedding 自带 query prompt**：日志里 `Loaded 1 prompt with these keys: ['query']` 说明模型内置了查询指令前缀，`query_instruction` 配置实测无提升故默认留空——**配置项存在的理由要用实验说话**。

## 方言对照表（sqlite-vec vs pgvector）

| 维度 | sqlite-vec | pgvector |
|---|---|---|
| 表结构 | 文本表 + vec0 虚表，rowid 关联 | 单表，`embedding vector(N)` 就是一列 |
| KNN 语法 | `WHERE embedding MATCH ? AND k = ?` | `ORDER BY embedding <=> %s LIMIT %s` |
| 向量传参 | `serialize_float32` 二进制 blob | `'[1,2,3]'::vector` 文本转换 |
| 自增主键 | `INTEGER ... AUTOINCREMENT` | `BIGINT GENERATED ALWAYS AS IDENTITY` |
| 扩展 | pip 包自带 | `CREATE EXTENSION vector` |
| 距离语义 | L2 距离（归一化后可换算） | `<=>` 直接是余弦距离 |

## 补丁追加：嵌入云端化 + 两个真实教训

### 性能驱动选型（实测数据）

本地 Qwen3-Embedding-0.6B（CPU）：**7.5 秒/块**，全量灌库 ~15 分钟 → 换 DashScope 云端 API：131 块 3.5 分钟，查询嵌入秒级。**嵌入是典型的「上云更划算」负载**——小数据量、无状态、对延迟不极端敏感。本地模型留给数据敏感或离线场景。

### 教训 1：语料自污染（面试金句素材）

把本学习计划灌进知识库后，「retry 组有哪些字段」的检索被计划文档里**原样记录了这个问题的复盘章节**劫胡（重排分 0.997 vs 正答案块 0.806）。根因：reranker 擅长判断「问题与文本的匹配」，但分不清「包含问题的文本」和「回答问题的文本」。生产含义：**知识库内容治理**——meta 文档（复盘/日志）与知识文档要分库或打标过滤。

### 教训 2：阈值要用数据校准

`MIN_RERANK_SCORE` 从拍脑袋的 0.01 修正为 0.1，依据是 4 个问题的实测分布：无关问题最高 0.055，真实问题最低 0.35，取中间带。这就是 M4 评估体系的最小雏形：**任何拍脑袋的参数，都该有一组校准数据**。
