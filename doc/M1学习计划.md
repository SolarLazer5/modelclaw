## 阶段 1 · 持久化层 `session_store.py`（1 天）

**对照笔记**：`存储.py` 里的 `store = {}` + `get_history(session_id)` 是内存版；本模块是它的「数据库升级版」。

精读顺序（每个函数都要能回答「为什么这样写」）：

- [x] `SCHEMA`：为什么拆两张表？`messages.id` 用自增整数而不是时间戳排序，好处是什么？
- [x] `_db()` 上下文管理器：**重点**。理解 `with sqlite3.connect()` 只提交事务、**不关闭连接**，Windows 下文件被锁的 bug 是怎么来的。试读 `contextlib.contextmanager` 的官方文档示例。
- [x] `_new_session_id()`：同秒冲突的处理方式（`_2` 后缀）。
- [x] `create_session()`：`INSERT OR IGNORE` 的幂等语义——为什么 `--session` 重复指定同一个 ID 不会报错？
- [x] `add_message()`：一个方法里做了三件事（插消息、刷新 `updated_at`、首轮自动起标题）。找到 `CASE WHEN title = ''` 这段 SQL，理解「只在标题为空时写入」。
- [x] `find_session()`：精确匹配 → LIKE 模糊匹配 → 0 个/多个匹配的不同报错。对比 `modelclaw.py` 里 `find_result_file()`，体会**同一套交互模式在两个功能里的复用**。
- [x] `list_sessions()`：SQL 子查询统计每个会话的用户轮数。

**动手实验**

**自测题**
1. 为什么每个操作都新开连接、用完即关，而不是在 `__init__` 里保存一个长连接？

   `答：这是为了防止发生文件句柄被占用的异常情况`

   `【批改】⚠️ 不完整。句柄泄漏（Windows 文件锁）只是四个理由之一，且不是最主要的——最主要的
   理由是"事务边界清晰"，这一点没答出来。`

   `【标准答案】四个理由：① 事务边界清晰——每次开连接 = 开一个事务，with conn 正常退出提交、
   异常回滚，关连接保证落盘；每次操作互不污染，回滚边界天然明确。② 自愈——连接可能失效（系统
   休眠、文件被移动、网络盘断开），每次新连接拿到的都是"新鲜"的。③ 防句柄泄漏——长连接忘关就
   是 with sqlite3.connect() 只提交不关闭的 Windows 文件锁 bug（你答的这一点）。④ 多线程安全
   ——SQLite 连接非线程安全，每操作一个连接天然规避。代价（每次连接的开销）在本场景（聊天 CLI，
   每秒几次操作）完全无感——用微小性能换正确性和简单性。`

2. 如果不用 `conn.row_factory = sqlite3.Row`，代码会难写在哪？

   `答：无法通过列名访问`

   `【批改】✅ 正确。可补一句"为什么难写"的具体画面。`

   `【标准答案】不设 row_factory 时，查询返回的行是元组，只能按下标 r[0] 取值——必须死记列顺序，
   SQL 的 SELECT 清单改一个列，所有取数下标都可能错位，脆弱且难读。设 sqlite3.Row 后行对象同时
   支持 r["session_id"]（按列名）和 r[0]（按下标），可读性与可维护性兼得。`

3. `delete_session` 里为什么要手动删两张表，而不是依赖 `ON DELETE CASCADE`？（提示：SQLite 的外键默认是关的）

   `答：两个原因，SQLite 的外键默认是关的，所以加了ON DELETE CASCADE也没用，其次代码本身也没给REFERENCES加ON DELETE CASCADE约束`

   `【批改】✅ 正确，两点全中。可再补一层"为什么不顺手把外键打开"。`

   `【标准答案】① SQLite 的外键检查默认关闭（需 PRAGMA foreign_keys=ON 且每个新连接都要执行，
   只对当前连接有效，漏开就静默失效），所以即使写了 ON DELETE CASCADE 也不会生效；② 本项目的
   schema 里 REFERENCES 后本来也没写 ON DELETE CASCADE。如果 delete_session 只删 sessions 行，
   messages 里会残留"孤儿消息"——指向不存在的会话，永远占空间还查不出来。手动两条 DELETE
   （先子表 messages 后父表 sessions）是不依赖外键开关、把一致性责任放在唯一入口的代码逻辑里的
   写法，更直白可靠。`

**自测题**

1. 摘要触发后，DB 里被摘要的原始消息为什么要删？不删会怎样（下次请求发生什么）？

   `答：如果不删，原始消息会一直占用上下文，总量始终超标，并且会发生重复的摘要总结，引发不必要的模型调用`

   `【批改】✅ 基本正确，两个核心后果都答到了。可再补两个后果和一句根因总结。`

   `【标准答案】根因：build_context 是无状态的，每次调用都从 DB 全量重读历史，触发判断
   （count_tokens > 6000）看的是"现存消息的总量"。删除已摘要的消息，信息才算真正迁入摘要、
   总量降下来，触发条件才可能变假——摘要成为一次性状态迁移。不删的后果有四：① 每轮请求总量
   都超标 → 每次都对同一批 head 重复摘要：白烧 LLM 调用、响应变慢；② 摘要反复"合并"同一批
   内容 → 摘要臃肿、细节失真；③ 旧消息既在 messages 又等价于在 summary → 重复占 4000 预算，
   最近对话反被挤出去；④ messages 表无限膨胀，文件越变越大。`

2. 「滚动摘要」和 `存储.py` 笔记里旧版 `ConversationSummaryBufferMemory` 的区别是什么？（提示：新版摘要是每次现算还是持久化的？本项目选了哪种，为什么？）

   `答：本项目摘要每次进行动态计算决定是否生成摘要，同时本项目在摘要总结后还进行了上下文窗口裁剪，同时为了防止数据库message表无限增长，对head进行摘要总结时，会删除原始信息，只留摘要在session中，并将这个摘要放进系统提示词中与已有摘要进行融合，所以本项目更加偏向于真实企业工程化实际项目`

   `【批改】⚠️ 方向对，但没击中提示的核心对比。你答到的"删除原始信息、摘要融合、工程化"都对；
   但题目问的核心是"摘要是每次现算还是持久化的"。你说的"每次动态计算决定是否生成摘要"指的是
   触发判断，不是摘要的存储方式——这是两个概念，答题时要分清。"每次现算 vs 持久化"这对对比
   没明确说出来。`

   `【标准答案】笔记旧版（存储.py 的 summarize_if_needed）：摘要是每次调用时临时生成、用完即弃
   的——原始消息永久保留在内存历史里（无损、可随时换策略重算），但存储是内存 dict（重启即失），
   且每次超限都要重新压缩全部旧历史（无增量合并，更贵）。本项目：摘要持久化到 sessions.summary
   字段（跨调用、跨进程存在），被摘要的原始消息从 messages 表物理删除（不可逆），且新摘要与
   已有摘要做增量滚动合并（_SUMMARY_PROMPT 里的"把新内容合并进已有摘要"）。选持久化+删除的原
   因：历史必须落盘（CLI 重启后要能 --resume）+ build_context 无状态全量重建（不删则触发条件
   恒真、每轮重复摘要）+ 跨进程使用。代价：信息不可逆，摘要质量成为生命线；笔记版则胜在透明、
   无损、可调试——那是教学式取舍，这是工程化取舍。`

3. 为什么摘要调用要用非流式的 `complete()` 而不是流式的 `ask()`？

   `答：摘要总结应该是一种后台的行为，而ask会在终端打印，如果摘要总结也要打印，会显得很怪，并且摘要总结要存库，所以返回值期望直接返回摘要字符串而不是dict`

   `【批改】✅ 正确，两个理由都命中且有代码证据：ask() 内部会 print("=== Thinking ===") 等
   分幕标题和正文（complete() 的 docstring 自述 "streaming output would just pollute the
   terminal"），且返回 {"reasoning", "answer"} 字典而非 str。可再补第三个理由。`

   `【标准答案】三个理由：① 副作用——ask() 是"带舞台效果的流式接口"，边收边往终端打印 Thinking/
   Final Answer 标题，摘要作为静默后台工序绝不该打扰用户屏幕；② 返回类型——ask() 返回
   reasoning/answer 字典，_summarize 的调用方需要能直接存库的完整 str，取 ["answer"] 还得处理
   reasoning 部分的去留；③ 原子性——complete() 要么返回完整字符串、要么重试耗尽后抛异常，与
   "摘要失败就不删原始消息"的安全逻辑严丝合缝；ask() 流式中断会留下已打印的半截内容，重试还会
   重复打印。`

4. token 计数是**近似**的（cl100k_base 不是 DeepSeek 的真实分词器）。这个误差在什么情况下会有实际影响？工程上怎么兜底？（提示：`max_context_tokens` 为什么默认 4000 而不是顶着模型上限）

   `答：如果基数不大，那么技术的误差也不会太大，通常在一个可接受的范围内，如果基数变大，那么计算的误差也随之增大，这就有可能突破模型上下文容量能力边界，导致出现问题，这也就是经常会实际发生的一个问题，定义合理的上下文管理策略阈值，防止这种情况的发生，进行兜底`

   `【批改】⚠️ 部分正确。两处要修：① "基数小误差就小"不是关键——误差是百分比性质，基数再大，
   只要离硬边界远就无害；真正的问题是"估算值贴近硬边界"（模型真实窗口），以及唯一不受 4000 闸门
   约束的安全网消息。② 兜底部分太泛，没答出提示的核心。`

   `【标准答案】误差只在"估算值贴近硬边界"时才有实际影响。系统里有两类边界：软边界（6000 触发线
   /4000 预算线）天然吸收误差——估错几个百分点不改变行为；硬边界（模型真实上下文窗口）才咬人，
   且只咬"低估"一种情况。最大的兜底手段就是提示问的答案本身：max_context_tokens 默认 4000 而
   不顶着模型上限（如 32K）——大余量让估算误差永远够不着硬边界（低估 20% 也才 4800）。配套兜底：
   ① max_tokens=2048 给模型回复预留座位；② 阈值全部在 config 的 memory 组，换模型后实测校准即
   可，不改代码；③ 上下文超长是 400 类错误，不在 RETRYABLE_ERRORS 里——快速失败、响亮报错，
   不静默劣化；④ 唯一例外是安全网放行的单条超长消息（它不受 4000 约束），但单条消息通常远短于
   模型窗口，风险现实中几乎不兑现。`

**自测题**
1. 单发 `chat "..."` 也会落一个会话。这个设计的好处和代价各是什么？

   `答：好处是保存的该会话的对话历史，方便用户反复查阅，或者通过该会话id进行resume，来继续该对话，代价是会增大数据量（数据库持久化存储）`

   `【批改】⚠️ 基本正确。「可查阅/可 resume」和「占存储」两个点都答到了，但好处漏了最有工程价值
   的一条（路径统一），代价也只答了最轻的一条。`

   `【标准答案】好处：① 一次性的提问也进入持久历史，可 --resume 续聊、可 sessions 列表查阅；
   ② 更关键的是路径统一——单发 chat "..." 和多轮 REPL 走完全相同的存储代码（add_message →
   build_context → ask → add_message），没有为单发特判任何分支，行为一致、代码无分叉；
   ③ 配合 --session 指定 ID，单发还能当作「往某个长期会话里补一句话」。
   代价：① 随口一问也永久落库——sessions 列表被大量无标题的一次性会话污染（list_sessions 会
   看到很多 (空) 标题）；② 隐私语义：用户未必意识到随手的问题被持久保存，敏感内容没有擦除
   通道；③ 数据库持续增长。
   一个值得指出的不对称：结果文件有 --no-save 开关，会话落库却是无条件的——说明作者把「会话」
   视为一等公民数据。若在意可加 --no-session 开关，但当前规模下必要性低。`

2. `--system` 参数存在 DB 里吗？`--resume` 时换个 system 会发生什么？这个设计合理吗？

   `答：system 参数不会存在 DB 里，它是在builderContext后在程序中存在的，--resume时换个system会改变系统提示词，方便再cli中随时定义模型的回复人设，这个设计从单cli使用上来说合理，如果落地到多用户，可以将system持久化存储到数据库中方便根据不同的用户来决定采用的系统提示词`

   `【批改】✅ 基本正确，三个要点都答到了（不存、会替换、单 CLI 合理/多用户该存）。可再补两个
   层次：「会发生什么」要说具体——这是一次「静默人设切换」，有隐性代价；以及一个不存的自洽性论据。`

   `【标准答案】不存。sessions 表的 schema 只有 session_id/title/summary/created_at/updated_at
   五列；system 与 --model/--temperature 同为纯调用期参数——每次 chat 启动时用当时的值，
   build_context 只负责把它拼到 context 最前面，用完即弃。
   --resume 换 system 会发生什么：旧 system 在 DB 里零痕迹，新 system 直接接管后续所有轮次；
   但历史消息和滚动摘要都是旧人设下产生的——模型以新人设解读旧历史，即「静默人设切换」。技术
   上无任何损坏，代价有三：人设漂移导致前后回答风格/口径不一致；摘要与新人设权重不匹配；
   对话不可复现（只看 DB 无法重建「当时它是在什么 system 下答的」）。另一面它也算特性：CLI
   场景下可以故意中途切人设（前半场翻译助手、后半场代码审查）。
   合理性：单用户 CLI 下合理——system 是随手可换的旋钮而非契约，且与 model/temperature 待遇
   自洽；若演进到多租户服务，system 就应入库成为会话契约的一部分，--resume 时校验或拒绝不一致。`

# M1.5 · 可插拔存储后端（SQLite / PostgreSQL）

> 在完成阶段 1 之后插入学习本章节。它回答一个问题：**怎么把「能跑的代码」升级成「能演进的架构」**。

## 背景认知（先建立正确观念）

- 「生产级 = MySQL/PG」是误区。Chrome、微信、LangGraph 本地态都用 SQLite——**单用户本地 CLI 的正确生产选型就是 SQLite**（零部署、事务完整、免运维）。
- 真正的生产级问题是：**当产品从 CLI 演进到多用户服务时，存储层能不能换？** 企业的答案是 Repository 模式（仓储模式）+ 依赖倒置：上层只依赖抽象接口，底层实现可插拔。
- 选 PostgreSQL 而不是 MySQL 的原因：M3 RAG 需要 pgvector 向量检索，PG 一库覆盖关系 + 向量；AI 应用栈（LangGraph PostgresSaver、Supabase）以 PG 为主流。

## 阶段 6 · 架构改造精读（0.5 天）

- [x] 读 `session_store.py` 顶部：`SessionStore` ABC 的 12 个抽象方法——**接口即契约**。思考：为什么抽象层定义好之后，`modelclaw.py` 和 `context_engine.py` 一行都不用改？（这就是依赖倒置：上层依赖抽象，不依赖具体实现）
- [x] `create_session_store()` 工厂：为什么 PostgresSessionStore 的 import 写在函数内部？（惰性导入——没装 psycopg 的用户只要不用 PG 后端就永远不报错）
- [x] 对照读 `postgres_store.py` 与 `SqliteSessionStore`：**同一份逻辑，两种方言**。

## SQL 方言差异对照表（面试可直接讲）

| 维度 | SQLite | PostgreSQL |
|---|---|---|
| 占位符 | `?` | `%s`（psycopg） |
| 自增主键 | `INTEGER PRIMARY KEY AUTOINCREMENT` | `BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY` |
| 幂等插入 | `INSERT OR IGNORE` | `INSERT ... ON CONFLICT DO NOTHING` |
| 字典行 | `sqlite3.Row` | `psycopg.rows.dict_row` |
| 建库 | 文件即库，无需建 | 无 `CREATE DATABASE IF NOT EXISTS`，需连维护库查 `pg_database` 再建（且 DDL 要 autocommit） |
| 取插入 id | `cursor.lastrowid` | `INSERT ... RETURNING id` |
| 连接语义 | `with conn:` 只提交不关连接（M1 的坑） | psycopg3 的 `with conn:` 提交**并**关闭 |
