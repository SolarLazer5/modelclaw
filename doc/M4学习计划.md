## 阶段 1 · M4a0 LangChain 主链路（1 天）★本阶段第一个硬知识

**主题：把框架接进一个已有工程，而不是从零开始用框架。**

- [x] 读 `llm_langchain.py` 顶部 docstring + `ModelScopeChatOpenAI`：**验证尖刺复盘**——实测发现 langchain-openai 1.7 的 `_convert_delta_to_message_chunk` 丢弃 `reasoning_content`（它只适配官方 DeepSeek 格式），子类化重写 `_convert_chunk_to_generation_chunk` 把字段救回 `additional_kwargs`

- [x] 理解补丁点的选择：为什么覆盖的是实例方法 `_convert_chunk_to_generation_chunk` 而不是模块函数 `_convert_delta_to_message_chunk`？（前者可子类化，后者是模块级函数改不动——读框架源码找扩展点的能力）

  [^]: 选择覆盖 `_convert_chunk_to_generation_chunk` 而非 `_convert_delta_to_message_chunk`，根本原因是 Python 的绑定机制：实例方法通过 `self` 动态查找，子类同名定义即可拦截（super() 形成"只加不改"的叠加）；模块级函数被内部调用方硬绑定，猴子补丁连模块内部调用都拦不住，且全局副作用大、随官方升级失效。这背后是通用方法论：**读框架源码定位丢失点，沿调用链向上找到第一个"类方法形态的扩展点"下刀——补丁不追求打在案发现场，而追求打在改得动、影响面小、能跟官方升级共存的位置**。

- [x] `create_llm` 的 `with_retry` 映射：config 里的 `max_attempts/initial_wait/backoff_multiplier/max_wait` → `exponential_jitter_params`。LangChain 的重试底层就是 tenacity——你 M1 学的那个库

- [x] `stream_events()` 生成器：为什么把流式抽成 `(kind, text)` 事件流？（CLI 打印和 HTTP SSE 两个消费者共享同一生产者——阶段 5 会用到）

1. 为什么判分链和答题链要用分开的 LLM 调用？（笔记原话：避免同一个链对自己的结果做主观判断）

   `答：略`

2. 5 个样本的准确率有多少统计意义？生产上怎么办？（扩大 n、固定测试集、跟踪趋势而非绝对值）

   答：5 个样本的准确率统计意义趋近于零：n=5 时每道题占 20 个百分点，80% 的 95% 置信区间宽约 ±35%，真实水平可能落在 45%~100% 之间的任何地方，系统改动的效果完全淹没在噪声里。它只能当冒烟测试用（识别 0%/100% 这类整体故障），不能当效果度量。

   生产的标准做法有三条：

    ① **扩大 n**——误差随 √n 收窄，n=100 才能分辨 10 个点以上的差异，n=400 到 5 个点；题目还要分层覆盖各种题型，并用"精度需求 ↔ LLM 调用成本"的预算权衡定 n；

    ② **固定测试集**——LLM 自动生成的题只是初稿，经人工筛选后冻结入库、版本管理。随机抽题的评估混入了"题目难度"这个不可控变量，只有同一张卷子才能让分数差异干净归因于系统改动；

    ③ **跟踪趋势而非绝对值**——单次绝对分数会随裁判严格度、模型版本整体漂移，不构成行动依据；按时间归档报告、固定题集反复重跑，曲线的升降才是每个改动功过的判决书。

   **总结：小样本的准确率不是测量，是占卜；生产的评估体系 = 足够大的固定题集 + 同卷重跑 + 看趋势。评估数字的价值不取决于它多精确，而取决于你能把分数变化归因到哪个改动上**

## 阶段 5 · M4d FastAPI 服务化（1 天）

- [x] 读 `server.py`：端点如何复用已有模块——`create_app()` 里只做组装，零业务逻辑

- [x] `/chat/stream` 的 SSE：`stream_events()` 生成器在这里第二次消费（阶段 1 的伏笔回收）。理解 SSE 格式（`data: {...}\n\n`）

  SSE：一条不关闭的 HTTP 响应，服务器往里一段段写

  `return StreamingResponse(gen(), media_type="text/event-stream")`

  - `media_type="text/event-stream"`：告诉客户端"这不是一个普通 JSON 响应，而是一条事件流"；

  - `StreamingResponse` 包住 `gen()`：FastAPI 不会等生成器跑完，而是每拿到一个 yield 出来的字符串就立刻发给客户端。

    **SSE 的格式：两个约定，data: 前缀和 \n\n 结尾**

    如：`data: {"type": "answer", "text": "你好"}`

    代码：`f"data: {json.dumps({'type': kind, 'text': text}, ensure_ascii=False)}\n\n"`
    实际产生的文本（注意结尾是两个换行）：`'data: {"type": "reasoning", "text": "用户在打招呼"}\n\n'`

- [x] 关键认知：**服务化后 PG 后端的意义才真正兑现**——多并发请求共享会话状态，SQLite 单文件在这里会成为瓶颈

  [^]: SQLite 面向本地化：轻量、单文件、单用户单进程的场景天然适合，CLI 时代选它正确。产品升级为多用户 HTTP 服务后，访问模式从串行变成并发，SQLite 的文件级锁成为天花板；PostgresSQL 以行级锁 + MVCC 支撑高并发。为此项目实现了可插拔双后端，工厂 + 契约测试保证行为一致，升级时一行配置切换（外加 PG 环境就绪），同一个接口同时服务"本地个人工具"和"多用户商业产品"两种形态

- [x] 实验：`serve` 起服务，CLI 聊一轮，再 curl /chat 带同一个 session 续聊——两个客户端共享同一套会话

  [^]: **实验验证的是"换客户端记忆不断"这个产品能力；高并发是同一套 PG 后端的另一份红利，两者互不担保，也互不亏欠**

**自测题**
1. 为什么 `/chat/stream` 的 `done` 事件里才写库（add_message）？（流中断不写半成品）

   代码:

   `def gen():
       answer_parts = []
       for kind, text in stream_events(cfg, messages):   # ← 流式产出中
           if kind == "answer":
               answer_parts.append(text)
           yield ...
       store.add_message(sid, "assistant", "".join(answer_parts))  # ← 流跑完后才执行
       yield f"data: ...done...\n\n"`

   关键在 yield 的行为：每次 yield 把控制权交还给框架去发送数据(`return StreamingResponse(gen(), media_type="text/event-stream")`)，下次从 yield 处继续。**如果客户端中途断开连接（关页面、断网、取消请求），框架会直接放弃这个生成器——循环退出，但循环后面的代码一行都不会执行。** 这个"半拉子执行"的语义，在这里恰恰是被利用来保护数据完整性的。所以 done 事件的准确含义是：**它是"写库成功、对话完整落盘"发给客户端的信号**

2. 如果 100 个用户同时调 /chat，现在的架构瓶颈在哪？（同步阻塞 → uvicorn workers / 异步化）

   - uvicorn 同步路由默认线程池只有 **40 个线程**；
   - 100 个用户同时来 → 40 个线程瞬间占满，剩下 60 个请求**排队等线程**，而每个被服务的请求要 15 秒才放人——队越排越长，后来的请求超时。**昂贵的资源（线程）被廉价的等待（网络 IO）占着**。
   - **两条扩容路线**
     1. **加 uvicorn workers**——开多个进程（`uvicorn --workers 4`），每个进程有自己的 40 线程池，总容量变成 4 倍。这是横向堆机器/堆进程的思路，简单直接，但单机能开的进程数受 CPU 和内存限制，且每个进程都重复加载模型客户端等资源。
     2. **异步化**——把路由改成 `async def`，HTTP 客户端换成异步版本（httpx.AsyncClient）。核心原理：**异步模型里，一个等待网络响应的请求几乎不占资源**——事件循环发现请求在等网络，就挂起它去服务别人，响应到了再唤醒。一个事件循环用单线程就能同时"挂着"成百上千个待完成的 LLM 请求，等待从"消耗一个线程"变成"占一条循环里的记录"。同样 100 个并发请求，异步化之后资源占用从"100 个线程"降到"1 个线程 + 100 条挂起记录"。
